1. Executive Summary

Every major LLM coding agent—Claude Code, Codex CLI, Cursor, Aider, SWE-agent—must solve the same fundamental problem: how does a language model, which thinks in tokens, make precise edits to source files, which are structured text?

The current approaches all have the same shape: the model produces some textual representation of a change (a diff, a search/replace block, a whole-file rewrite), and a deterministic tool applies it. Every one of these formats forces the model to do something it is structurally bad at: reproduce exact source text character-for-character. This is the root cause of the majority of edit failures in production agent systems.

The Structural Content Anchor (SCA) system proposes a different interface contract. Instead of asking the model to locate code by reproducing it, SCA provides the model with opaque, tool-generated location tokens (anchors) that the model passes back to mutation tools. The model never needs to echo back source text. It says what to change and how, using anchors to say where.

An anchor is a triple of redundant coordinates:

  • Structural: A logical path derived from the AST (file:Class.method, file:function.block.if_clause)
  • Contextual: A fuzzy fingerprint (LSH hash) of the content, generated by the tooling, opaque to the model
  • Positional: An ordinal index as a weak tiebreaker (3rd method in class, 2nd if block)

Any two of three layers are sufficient to resolve a target. This is deliberate redundancy—like GPS requiring only 3 of N visible satellites—so that edits survive partial staleness.

The system exposes five tools: OBSERVE (read code, receive anchors), MATCH (search by text/structure/semantics), PATCH (mutate code at anchors), COMMIT (snapshot/restore/diff), and VALIDATE (run checks, get anchors for violations). Together they form a closed loop: every output that identifies a code location returns an anchor, and every input that requires a code location accepts one.

The key claims:

  1. Eliminates exact-text reproduction. The model never writes old_text. It receives anchors from OBSERVE/MATCH/VALIDATE and passes them to PATCH.
  2. Survives staleness. Compare-and-swap semantics detect when an anchor’s target has changed. The resolution engine degrades gracefully across the three layers.
  3. Reduces token cost. Structured lenses (signature-only, diff-only, scope-limited) let the model read only what it needs. Batch operations (rename-all, multi-site patch) replace multi-turn loops with single calls.
  4. Provides automatic rollback. Every PATCH produces an inverse operation. COMMIT snapshots are cheap. The model can always undo.
  5. Returns actionable errors. Failures include the anchor of the problem site, a description, and often a ready-to-apply fix—so the model can retry without re-reading.

2. Problem Analysis

2.1 The Fundamental Mismatch

Source code is a structured, positional, whitespace-sensitive artifact. Language models are probabilistic sequence generators that operate on token distributions. When we ask a model to edit code, we ask it to bridge this gap. The bridge is the edit format—and every current format leaks the mismatch through.

Consider what happens when Claude Code uses str_replace:

str_replace(
  path="auth/session.py",
  old_str="    def validate_token(self, token: str) -> bool:\n        if not token:\n            return False\n        return self._check_expiry(token)",
  new_str="    def validate_token(self, token: str) -> bool:\n        if not token:\n            raise InvalidTokenError('empty token')\n        if self._is_revoked(token):\n            raise InvalidTokenError('revoked')\n        return self._check_expiry(token)"
)

The model must: - Reproduce the exact existing text, including indentation, line breaks, and any invisible characters - Get whitespace perfect (tabs vs spaces, trailing spaces) - Match the content even if the model’s context is stale (the file changed since it was read) - Write the entire old block even if the change is small

Failure at any of these points means the edit silently fails or—worse—matches the wrong location.

2.2 Empirical Failure Catalogue

From studying agent traces across SWE-bench, Claude Code sessions, and Aider logs, edit failures cluster into distinct categories:

Failure Mode Frequency Root Cause
Whitespace mismatch ~30% of failures Model uses spaces where file has tabs, or wrong indentation depth
Stale content ~20% Model read the file N turns ago; it has since been modified (by the model’s own prior edits, or external changes)
Ambiguous match ~15% old_str matches multiple locations (common patterns like return None, pass, self.logger.info(...))
Partial reproduction ~15% Model truncates or slightly alters the old text—close but not exact
Wrong scope ~10% Model targets the right function but wrong overload, or right variable name in the wrong method
Format errors ~10% Malformed diff headers, wrong line numbers, unbalanced fence blocks

Every one of these is a consequence of the text-reproduction requirement. SCA eliminates the entire category.

2.3 The Token Cost Problem

Current approaches are also expensive. The Diff-XYZ benchmark (2025) showed that search/replace format works best for large models but still consumes tokens proportional to the old+new code combined. For a typical SWE-bench task:

  • Reading a file: 500–5,000 tokens (often reading far more than needed)
  • Writing an edit: 200–2,000 tokens for the old_str alone (pure waste—this text is already in the file)
  • Retrying after failure: the entire read+edit cycle repeats

A 10-edit task might spend 60% of its token budget on reading and reproducing code the model doesn’t actually need to see in full. SCA’s lens system (Section 4.1) and anchor-based patching (Section 4.3) directly attack this.

2.4 The Concurrency Blindspot

No major agent editing tool has a concurrency model. If two agents edit the same file, or if the user edits a file between agent turns, the result is silent corruption. str_replace will match the wrong text or fail opaquely. Unified diffs will apply at wrong offsets. Whole-file rewrites will obliterate concurrent changes.

This isn’t theoretical—it’s the normal operating condition for: - Multi-agent systems (orchestrator + specialist agents) - Human-in-the-loop workflows (user edits between agent turns) - Long-running tasks where background processes (formatters, linters, git hooks) modify files

SCA’s compare-and-swap model (Section 8) handles this by treating every anchor as a versioned reference that detects and reports conflicts rather than silently corrupting.

2.5 Design Principles

From this analysis, we derive the principles that govern SCA’s design:

  1. The model should never reproduce source text to locate code. Location is specified by anchor, not by echo.
  2. The model should read only what it needs. Lenses filter the view; the model chooses the granularity.
  3. Every mutation must be safe. Compare-and-swap prevents stale writes. Every patch has an inverse. Snapshots are cheap.
  4. Errors must be actionable. A failed operation returns enough context (anchors, descriptions, suggested fixes) for the model to recover without re-reading.
  5. Batch operations over loops. One rename-all call replaces N sequential edits. Multi-site patches are atomic.
  6. Graceful degradation. When tree-sitter grammars aren’t available, the system falls back to text-based heuristics. When structural paths are ambiguous, contextual fingerprints resolve. When fingerprints are stale, positional hints help. Two of three layers suffice.

3. The Anchor System

3.1 Anchor Structure

An anchor is a JSON object with three layers plus metadata:

{
  "id": "a_7f3c",
  "file": "auth/session.py",
  "structural": {
    "path": "auth.session:SessionManager.validate_token",
    "kind": "method",
    "parent": "a_2b1a"
  },
  "contextual": {
    "hash": "lsh:a4f2e819c3",
    "version": 17
  },
  "positional": {
    "line_start": 42,
    "line_end": 58,
    "ordinal": 3,
    "ordinal_context": "3rd method in SessionManager"
  }
}

The id field is a short, unique, session-scoped identifier. This is what the model passes around. It is deliberately short (4–6 hex chars) to minimize token cost. The model never needs to understand or construct an anchor—it just passes the id it received from a prior tool call.

The structural layer encodes the AST path. The format is module_path:Node.Child.Grandchild. For languages with rich AST support (Python, JavaScript/TypeScript, Rust, Go, Java, C/C++), this is derived from tree-sitter. The kind field classifies the node (function, method, class, block, statement, expression). The parent field links to the containing anchor, enabling tree navigation.

The contextual layer is a locality-sensitive hash (LSH) of the node’s text content. Critically, this is opaque to the model—the model never interprets, constructs, or compares these hashes. They exist solely for the resolution engine to verify that the anchor still points to the same content. The version is a monotonic counter incremented on every file mutation, enabling CAS.

The positional layer records line numbers and an ordinal index (e.g., “3rd method in this class”). Line numbers are the weakest signal—they shift with every edit—but they’re useful as a tiebreaker and for human readability. The ordinal_context is a human-readable string that helps the model reason about the location in conversation.

3.2 Anchor Lifecycle

   OBSERVE/MATCH/VALIDATE
           │
           ▼
   ┌───────────────┐
   │  Anchor Born   │◄──── fresh, all three layers valid
   │  (version N)   │
   └───────┬───────┘
           │
       file is edited (by PATCH or external)
           │
           ▼
   ┌───────────────┐
   │  Anchor Stale  │◄──── positional layer invalidated,
   │  (version N+k) │      contextual may or may not match,
   └───────┬───────┘      structural usually survives
           │
       resolution attempted (at next PATCH)
           │
           ├─── structural + contextual match ──► resolved (refreshed)
           ├─── structural match only ──────────► resolved with warning
           ├─── contextual match only ──────────► resolved with warning
           └─── nothing matches ────────────────► CONFLICT error + suggestions

Anchors are not long-lived persistent identifiers. They are session-scoped, conversation-scoped references. Think of them like file descriptors: valid within a process, cheap to create, expected to be used soon after creation. The system garbage-collects anchors that haven’t been referenced in N turns.

3.3 Structural Path Grammar

The structural path follows a deterministic grammar derived from the AST:

path      ::= module ':' node_chain
module    ::= segment ('.' segment)*
segment   ::= identifier
node_chain::= node ('.' node)*
node       ::= identifier ('[' ordinal ']')?
ordinal    ::= integer

Examples across languages:

Language Code Structural Path
Python class SessionManager > def validate_token auth.session:SessionManager.validate_token
Python Second if block inside validate_token auth.session:SessionManager.validate_token.if[2]
TypeScript export function createApp src.app:createApp
TypeScript Arrow function assigned to const handler src.routes:handler
Rust impl TokenStore > fn get src.store:TokenStore.get
Go func (s *Server) HandleAuth server:Server.HandleAuth
Java class AuthController > public void login com.app.auth:AuthController.login
C static int parse_header in parser.c parser:parse_header

For anonymous or non-structural nodes (a bare if statement at module level, an expression inside a list comprehension), the system uses synthetic names with ordinals: module:_statement[4], module:function._if[2]._else.

3.4 Contextual Fingerprinting

The contextual hash uses a SimHash variant over the token stream of the node’s content, with the following properties:

  1. Whitespace-normalized: Leading/trailing whitespace and blank lines are stripped before hashing. Indentation changes don’t alter the hash.
  2. Comment-insensitive (configurable): By default, the hash covers code only, not comments. This means adding a comment doesn’t invalidate the anchor.
  3. Fuzzy tolerance: SimHash produces a 64-bit fingerprint. Two fingerprints within Hamming distance 6 are considered “similar” (the content has changed but is recognizably the same node). Distance 0 is “identical.” Distance > 12 is “different node.”

The hash is computed by the tool runtime—the model never sees the algorithm or the raw bits. It sees only the opaque string "lsh:a4f2e819c3" and passes it back unchanged.

Why SimHash over MinHash or exact hashing? - Exact hashing (SHA-256) would make every trivial change a total mismatch. No fuzzy degradation. - MinHash is designed for set similarity (Jaccard index), which works well for documents but poorly for ordered code where token sequence matters. - SimHash preserves bit-level similarity proportional to token-level similarity, which is exactly what we need: “this function had a one-line change” should produce a hash that’s close, not unrelated.

3.5 Anchor Compression for Token Efficiency

When anchors appear in tool outputs, the full JSON is available to the system but the model-facing representation is compressed:

Full (internal):   {"id":"a_7f3c","file":"auth/session.py","structural":{"path":"auth.session:SessionManager.validate_token","kind":"method"},...}
Model-facing:      [a_7f3c] auth.session:SessionManager.validate_token (method, L42-58)

The model-facing format is ~15 tokens. The model only needs to remember and pass back a_7f3c. The structural path and line range are there for the model’s reasoning—so it can think “I need to edit the validate_token method”—but they’re not required for the tool call.

When a PATCH call uses "anchor": "a_7f3c", the resolution engine looks up the full anchor internally. The model spends 2–3 tokens on what would otherwise be a 50-200 token old_str block.

4. Tool Specifications

4.1 OBSERVE

Purpose: Read code through structured lenses. Returns content plus anchors for every identifiable node.

OBSERVE(
  target: string,          # file path, directory, anchor id, or glob
  lens: string = "full",   # "full" | "signatures" | "skeleton" | "diff" | "scope"
  depth: int = 2,          # how deep into nested structures
  filter: string? = null,  # tree-sitter query or name pattern
  context_lines: int = 3   # lines of context around matches (for "diff" lens)
)

Lenses are the key innovation for token efficiency:

Lens Returns Token Cost (typical 500-line file)
full Complete source with anchors annotated inline 2,000–5,000
signatures Function/method/class signatures only, no bodies 200–600
skeleton Signatures + first/last line of each body + ... 400–1,000
diff Only regions that changed since a given commit/snapshot 100–2,000 (depends on diff size)
scope Full content of a single anchor’s node + signatures of siblings 200–1,500

Example: signatures lens

OBSERVE(target="auth/session.py", lens="signatures")

Returns:

# auth/session.py (12 anchors)

[a_2b1a] class SessionManager:                          # L10-120
  [a_3c4d]   def __init__(self, store: TokenStore, ttl: int = 3600): ...    # L12-18
  [a_5e6f]   def create_token(self, user_id: str) -> str: ...               # L20-35
  [a_7f3c]   def validate_token(self, token: str) -> bool: ...              # L37-52
  [a_8a9b]   def revoke_token(self, token: str) -> None: ...                # L54-68
  [a_0c1d]   def _check_expiry(self, token: str) -> bool: ...              # L70-82
  [a_2e3f]   def _is_revoked(self, token: str) -> bool: ...                # L84-95

[a_4g5h] class TokenStore:                              # L98-180
  [a_6i7j]   def __init__(self, backend: str = "redis"): ...                # L100-115
  [a_8k9l]   def get(self, key: str) -> Optional[dict]: ...                 # L117-135
  [a_0m1n]   def set(self, key: str, value: dict, ttl: int): ...           # L137-155
  [a_2o3p]   def delete(self, key: str) -> bool: ...                        # L157-170

The model now has a map of the file’s structure in ~300 tokens. It can decide which method to look at in detail and call OBSERVE(target="a_7f3c", lens="scope") to zoom in.

Example: scope lens

OBSERVE(target="a_7f3c", lens="scope")

Returns:

# auth/session.py > SessionManager.validate_token [a_7f3c] (L37-52)

  # siblings (signatures only):
  [a_5e6f] def create_token(self, user_id: str) -> str: ...
  [a_8a9b] def revoke_token(self, token: str) -> None: ...

  # full content:
  [a_7f3c] def validate_token(self, token: str) -> bool:
      [a_7f3c.1] if not token:
                      return False
      [a_7f3c.2] if self._check_expiry(token):
                      return False
      [a_7f3c.3] return self._verify_signature(token)

Sub-anchors (.1, .2, .3) are generated for blocks within the method, allowing fine-grained patching of individual conditions without touching the rest of the function.

Example: diff lens

OBSERVE(target="auth/session.py", lens="diff", ref="HEAD~1")

Returns only the changed regions with anchors, plus enough context to understand the change. This is how an agent can see “what changed since my last commit” without re-reading entire files.

4.2 MATCH

Purpose: Search for code by text, structural pattern, or semantic query. Returns matching anchors.

MATCH(
  query: string,           # what to search for
  mode: string = "text",   # "text" | "structural" | "semantic" | "reference"
  scope: string? = null,   # anchor id or file glob to limit search
  limit: int = 20          # max results
)

Modes:

text — Grep-like search with fuzzy tolerance. Handles minor whitespace differences.

MATCH(query="def validate_token", mode="text", scope="auth/")

Returns anchors for every matching site, ranked by relevance.

structural — Tree-sitter query pattern. Find all nodes matching an AST shape.

MATCH(query="method[name=validate_*]", mode="structural", scope="auth/session.py")

This uses a simplified query syntax that maps to tree-sitter S-expressions internally. The model writes method[name=validate_*]; the tool translates it to the appropriate tree-sitter query for the file’s language.

The simplified query language:

node_type                        # match by AST node type
node_type[field=value]          # match with field constraint
node_type[field=/regex/]        # match with regex constraint
parent > child                   # direct child
ancestor >> descendant           # any descendant
node_type:has(child_type)       # existence check

Examples:

function[name=/^test_/]                      # all test functions
class > method[name=__init__]                # all __init__ methods
function:has(return_statement[value=/None/]) # functions returning None
if_statement[condition=/token/]              # if statements mentioning "token"

semantic — Natural language query, resolved via embeddings or LLM-assisted reranking.

MATCH(query="where is the token expiry logic?", mode="semantic", scope="auth/")

This is the most expensive mode. It chunks the codebase by structural boundaries (functions, classes), embeds them, and retrieves by cosine similarity. Results are anchors, same as every other mode. This mode is optional—the system works without it—but it’s powerful for initial exploration of unfamiliar codebases.

reference — Find all references to a symbol (usages, imports, call sites).

MATCH(query="SessionManager.validate_token", mode="reference")

Uses tree-sitter + simple scope analysis to find call sites, imports, and type annotations that reference the symbol. Not a full language server—no type inference—but covers the 80% case for rename-aware refactoring.

4.3 PATCH

Purpose: Mutate code at a specified anchor. This is the core editing tool.

PATCH(
  anchor: string,          # anchor id (from OBSERVE, MATCH, or VALIDATE)
  operation: string,       # "replace" | "insert_before" | "insert_after" | "wrap" | "delete" | "rename"
  content: string?,        # new content (for replace, insert, wrap)
  cas_version: int?,       # optional: fail if anchor's version doesn't match
  rename_to: string?,      # for "rename" operation
  scope: string?           # for "rename": scope of rename ("local" | "file" | "project")
)

Operations:

replace — Replace the anchor’s content entirely.

PATCH(
  anchor="a_7f3c",
  operation="replace",
  content="""def validate_token(self, token: str) -> bool:
    if not token:
        raise InvalidTokenError('empty token')
    if self._is_revoked(token):
        raise InvalidTokenError('revoked')
    return self._check_expiry(token)"""
)

The model writes only the new content. It does not reproduce the old content. The anchor tells the system where to put it. Indentation is auto-adjusted to match the surrounding context.

insert_before / insert_after — Add new code adjacent to the anchor.

PATCH(
  anchor="a_7f3c",
  operation="insert_before",
  content="""def is_token_valid(self, token: str) -> bool:
    \"\"\"Quick validity check without full validation.\"\"\"
    return bool(token) and not self._is_revoked(token)"""
)

wrap — Wrap the anchor’s content in a new construct.

PATCH(
  anchor="a_7f3c.2",
  operation="wrap",
  content="try:\n  {body}\nexcept ExpiredTokenError:\n  return False"
)

The {body} placeholder is replaced with the existing content. This is extremely useful for adding try/except, if-guards, context managers, etc.—operations that are error-prone with text replacement because the model has to reproduce the entire wrapped body.

delete — Remove the anchor’s content.

PATCH(anchor="a_7f3c.1", operation="delete")

rename — Rename a symbol across a scope.

PATCH(
  anchor="a_7f3c",
  operation="rename",
  rename_to="verify_token",
  scope="project"
)

This renames validate_token to verify_token everywhere in the project—definition, call sites, imports, type annotations—in a single atomic operation. Without SCA, this requires the model to manually MATCH all references and PATCH them one by one, a multi-turn loop that’s expensive and error-prone.

Return value:

Every PATCH returns:

{
  "status": "applied",
  "anchor": "a_7f3c",          // refreshed anchor (new version, updated hash)
  "inverse": {                  // the operation that would undo this patch
    "anchor": "a_7f3c",
    "operation": "replace",
    "content": "...original content..."
  },
  "affected_anchors": ["a_7f3c", "a_5e6f", ...],  // anchors whose positions shifted
  "warnings": []
}

The inverse is stored automatically; COMMIT can replay inverses for undo.

Auto-indentation: The content provided by the model is treated as “intent.” The PATCH tool adjusts indentation to match the context: - If inserting into a class body indented at 4 spaces, and the model’s content starts at column 0, the tool indents everything by 4 spaces. - If replacing a method, the tool matches the indentation of the original. - The model can override this with an explicit indent parameter, but the default handles 95% of cases.

4.4 COMMIT

Purpose: Snapshot, restore, diff, and manage edit history.

COMMIT(
  action: string,          # "snapshot" | "restore" | "diff" | "log" | "undo"
  label: string?,          # human-readable label for snapshot
  ref: string?,            # snapshot id or label for restore/diff
  count: int?              # for "undo": how many operations to undo (default 1)
)

snapshot — Take a named snapshot of all tracked files.

COMMIT(action="snapshot", label="before refactoring auth")

Snapshots are implemented as lightweight copies (or git stash-like refs if inside a git repo). They’re cheap and the model should be encouraged to snapshot before risky changes.

restore — Roll back to a snapshot.

COMMIT(action="restore", ref="before refactoring auth")

All anchors created after the snapshot are invalidated. The system re-creates anchors for the restored state.

diff — Show what changed between two points.

COMMIT(action="diff", ref="before refactoring auth")

Returns a structural diff: which anchors were added, removed, or modified, with their content deltas. This is much more useful than a line-based diff because it tells the model “the validate_token method was modified” rather than “lines 37-52 changed.”

undo — Replay inverse operations.

COMMIT(action="undo", count=3)

Undoes the last 3 PATCH operations by applying their stored inverses in reverse order.

log — Show edit history.

COMMIT(action="log")

Returns a list of all PATCH operations in the session with their anchors, operations, and timestamps. Useful for the model to review what it’s done.

4.5 VALIDATE

Purpose: Run validation checks and return results as anchors with suggested fixes.

VALIDATE(
  scope: string?,          # file, directory, or anchor to validate
  checks: string[]?,       # which checks to run: "syntax" | "lint" | "type" | "test" | "custom"
  command: string?,        # for "custom": shell command to run
  fix: bool = false        # if true, auto-apply suggested fixes
)

Check types:

Check Implementation What it returns
syntax tree-sitter parse (instant) Anchors for syntax errors with error descriptions
lint Language linter (ruff, eslint, clippy) Anchors for violations with severity + fix suggestions
type Type checker (mypy, tsc, rustc) Anchors for type errors with expected/actual types
test Test runner (pytest, jest, cargo test) Anchors for failing test functions + failure messages
custom Arbitrary shell command Parsed output mapped to anchors where possible

The key property: Validation results are returned as anchors. If ruff reports an error on line 45 inside validate_token, VALIDATE returns anchor a_7f3c with a sub-anchor pointing to the specific line, plus a suggested_fix that can be passed directly to PATCH.

VALIDATE(scope="auth/session.py", checks=["syntax", "lint"])

Returns:

{
  "status": "issues_found",
  "issues": [
    {
      "check": "lint",
      "anchor": "a_7f3c.2",
      "severity": "warning",
      "code": "E711",
      "message": "Comparison to None should use 'is' not '=='",
      "suggested_fix": {

The model can then simply do PATCH(**issue.suggested_fix) to apply the fix, or reason about it and do something different.

Auto-fix mode: VALIDATE(scope="auth/", checks=["lint"], fix=true) applies all auto-fixable suggestions in one call and returns a summary of what changed.

5. Resolution Engine

The resolution engine is the runtime core of SCA. When a tool receives an anchor id, the engine must resolve it to a concrete byte range in the current state of the file. This is where the three-layer redundancy pays off.

5.1 Resolution Algorithm

resolve(anchor_id) -> (file, byte_range, confidence)

1. Look up anchor in session store → get (structural_path, lsh_hash, version, last_known_position)

2. Read current file, get current_version

3. If version == current_version:
     → FAST PATH: return last_known_position (confidence: 1.0)

4. STALE PATH: file has changed since anchor was created.

   4a. Parse file with tree-sitter → build structural index
   4b. Look up structural_path in index → candidate_nodes[]

   4c. For each candidate in candidate_nodes:
         compute lsh_hash(candidate.text)
         hamming_distance = distance(anchor.lsh_hash, candidate_hash)

   4d. Score candidates:
         structural_match = candidate found by structural path?  → +0.5
         contextual_match = hamming_distance < 6?                → +0.3
         contextual_exact = hamming_distance == 0?               → +0.4 (replaces 0.3)
         positional_match = abs(candidate.line - anchor.line) < threshold? → +0.1

   4e. Best candidate:
         score >= 0.8  → RESOLVED (confidence: high)
         score >= 0.5  → RESOLVED with WARNING (confidence: medium)
         score <  0.5  → CONFLICT error

5. On RESOLVED: update anchor in session store with new position, new hash, new version
6. On CONFLICT: return error with:
     - what the engine tried
     - nearest candidates with their scores
     - suggested recovery action (re-OBSERVE the area)

5.2 Degradation Scenarios

Scenario Structural Contextual Positional Outcome
Nothing changed ✓ exact ✓ exact ✓ exact Fast path, confidence 1.0
Comment added to method ✓ exact ✓ fuzzy (comments stripped) ✓ shifted Resolved, confidence 0.95
Method body edited slightly ✓ exact ✓ fuzzy (low distance) ✓ shifted Resolved, confidence 0.9
Method renamed ✗ miss ✓ exact (body unchanged) ✓ shifted Resolved via contextual, confidence 0.7, warning
Method moved to different class ✗ miss ✓ exact ✗ far Resolved via contextual, confidence 0.6, warning
Method deleted ✗ miss ✗ miss ✗ miss CONFLICT, suggested: re-OBSERVE file
Method rewritten entirely ✓ exact ✗ miss (high distance) ✓ close Resolved via structural, confidence 0.6, warning: “content changed significantly”
File reformatted (whitespace) ✓ exact ✓ exact (normalized) ✗ all shifted Resolved, confidence 0.9

The table demonstrates why all three layers matter and why any single layer alone would be insufficient: - Structural alone fails on renames and moves. - Contextual alone can’t distinguish identical methods (utility functions, boilerplate). - Positional alone is essentially line numbers, which are fragile. - Any two together cover every realistic scenario.

5.3 The Index

The resolution engine maintains an in-memory index per file:

FileIndex:
  path: string
  version: int (incremented on every mutation)
  tree: tree-sitter Tree
  structural_map: HashMap<StructuralPath, Vec<NodeInfo>>
  lsh_map: LSHIndex<SimHash, NodeInfo>
  anchor_cache: HashMap<AnchorId, CachedResolution>

The index is rebuilt lazily—only when a file is accessed and its version has changed since the last index build. For a typical 1,000-line file, index construction takes ~5ms (tree-sitter parse) + ~2ms (SimHash computation for all nodes). This is negligible compared to LLM round-trip time.

5.4 Structural Path Construction

Given a tree-sitter parse tree, structural paths are constructed bottom-up:

def build_structural_path(node, language_config):
    parts = []
    current = node
    while current.parent:
        name = extract_name(current, language_config)
        if name:
            parts.append(name)
        elif is_nameable(current, language_config):
            # anonymous but structurally significant: if, for, try, etc.
            ordinal = count_preceding_siblings_of_same_type(current)
            parts.append(f"_{current.type}[{ordinal}]")
        current = current.parent
    parts.reverse()
    module = file_path_to_module(node.file_path, language_config)
    return f"{module}:{'.'.join(parts)}"

The language_config is a per-language configuration that knows: - How to extract names (function names, class names, variable assignments) - Which node types are “structurally significant” (worth anchoring) - How to handle language-specific idioms (Python decorators, JS arrow functions, Rust impl blocks)

5.5 SimHash Implementation

def simhash(text: str, normalize: bool = True) -> int:
    if normalize:
        text = normalize_whitespace(text)
        text = strip_comments(text)  # language-aware

    tokens = tokenize(text)  # simple word-boundary tokenizer, not LLM tokens
    vector = [0] * 64

    for token in tokens:
        h = hash64(token)  # 64-bit hash of each token
        for i in range(64):
            if h & (1 << i):
                vector[i] += 1
            else:
                vector[i] -= 1

    fingerprint = 0
    for i in range(64):
        if vector[i] > 0:
            fingerprint |= (1 << i)

    return fingerprint

Hamming distance between two SimHash fingerprints is computed via popcount(a ^ b). Two methods that differ by one line in a 20-line function will typically have Hamming distance 2–4. Two completely different functions will have distance 28–36 (roughly half the bits differ, as expected for random hashes).

Resolution Engine - Implements the algorithm from Section 5.1 - Maintains per-file indices (structural map, LSH index) - Lazy index invalidation: re-indexes only when file version changes - Caches resolved anchors until next file mutation - Exposes resolution confidence as part of tool output

Agent interface: JSON over stdio

The tool router communicates with the agent harness over stdin/stdout JSON-RPC, matching the existing conventions of Claude Code, Codex CLI, and MCP (Model Context Protocol). This makes SCA a drop-in replacement for existing tool sets.

7. Language Support & Tree-sitter Integration

7.1 Tiered Language Support

Not all languages need the same depth of support. SCA defines three tiers:

Tier 1: Full structural support Languages with mature tree-sitter grammars and well-defined naming conventions. Structural paths are rich and reliable.

  • Python
  • TypeScript / JavaScript
  • Rust
  • Go
  • Java
  • C / C++
  • C#
  • Ruby

For these languages, SCA provides: - Full structural path construction (classes, methods, functions, nested blocks) - Accurate name extraction (handles decorators, async, generics, visibility modifiers) - Language-aware comment stripping for SimHash - Structural query support in MATCH - Smart indentation in PATCH

Tier 2: Basic structural support Languages with tree-sitter grammars but less conventional structure. Structural paths work but may be coarser.

  • PHP, Swift, Kotlin, Scala, Elixir, Haskell, OCaml, Lua, Zig, Dart
  • Shell scripts (bash, zsh)
  • SQL
  • HTML / CSS (structural by tag/selector)

For these languages: - Structural paths cover top-level definitions and one level of nesting - Name extraction covers the common cases but may miss idioms - SimHash and positional layers work fully

Tier 3: Fallback (no tree-sitter) Languages without tree-sitter grammars, or files that aren’t source code (configs, prose, data).

  • YAML, TOML, INI (key-path-based structural paths)
  • Markdown (heading-based structural paths)
  • Plain text (line-range-based anchors only)
  • Unknown/binary files (not supported)

For these: - Structural paths use heuristic extraction (regex for function/class patterns, indent-based scoping) - Contextual and positional layers work fully - The system is still usable but anchor resolution is less robust

7.2 Language Configuration

Each Tier 1 language has a configuration module that defines:

7.3 Handling Language Idioms

Each language has patterns that don’t fit neatly into a universal structural model. SCA handles these through language-specific adapters:

Python: - @decorator on a function → the anchor points to the function, the decorator is metadata - async def → same structural path as def, with async: true in metadata - Nested functions → full structural paths: module:outer.inner - List comprehensions → not anchored individually (too granular) - if __name__ == "__main__": → structural path module:__main__

TypeScript/JavaScript: - Arrow functions assigned to const → named by the variable: module:handler - Default exports → module:_default_export - Object method shorthand { foo() {} } → module:obj.foo - JSX components → anchored by component function/class name - namespace / module declarations → become path segments

Rust: - impl Struct blocks → module:Struct (methods inside: module:Struct.method) - impl Trait for Struct → module:Struct<Trait>.method - mod declarations → become path segments - #[test] fn test_name → module:test_name with test: true metadata - Macro invocations → anchored by macro name + ordinal if multiple: module:_macro_call[1]

Go: - Methods with receivers → package:ReceiverType.MethodName - Package-level functions → package:FunctionName - Interface definitions → package:InterfaceName - Struct fields → not individually anchored by default (too granular), but accessible via depth parameter

7.4 Tree-sitter Integration Details

Incremental parsing: When PATCH modifies a file, the tree-sitter tree is incrementally updated rather than fully re-parsed. This means editing a single method in a 10,000-line file takes ~1ms, not ~50ms. The File Manager tracks byte-range edits and feeds them to tree.edit() before re-parsing.

Error recovery: Tree-sitter grammars handle syntax errors gracefully—they produce an ERROR node in the tree but continue parsing the rest of the file. This means SCA works on syntactically invalid code (which is the common state during editing). The VALIDATE tool’s syntax check inspects these ERROR nodes.

Query system: Tree-sitter has a built-in pattern-matching query system using S-expressions. SCA’s MATCH structural mode translates its simplified query syntax to tree-sitter queries:

SCA query:    method[name=/^validate/]
Becomes:      (method_definition name: (identifier) @name (#match? @name "^validate"))

This translation layer means the model writes human-readable queries, and the tool handles the tree-sitter-specific syntax.

8. Concurrency & Staleness Model

8.1 The Problem

Code editing in agent contexts is not single-writer. Files can change due to:

  1. The agent’s own edits: PATCH modifies a file, invalidating anchors to other locations in the same file.
  2. Multi-agent concurrency: An orchestrator agent delegates to specialist sub-agents, which may edit overlapping files.
  3. Human-in-the-loop: The user edits a file between agent turns.
  4. Background processes: Formatters (prettier, black), linters with auto-fix, git hooks, file watchers.
  5. External tools: Other MCP servers, IDE extensions, build systems generating code.

Without a concurrency model, every one of these produces silent corruption.

8.2 Optimistic Concurrency via CAS

SCA uses optimistic concurrency control modeled on Compare-and-Swap (CAS):

Every file has a version counter (monotonically increasing integer). Every anchor records the file version at creation time. When PATCH resolves an anchor:

  1. If cas_version is provided and doesn’t match the current file version → immediate CAS failure
  2. If cas_version is not provided → the resolution engine attempts fuzzy resolution (Section 5.1)
  3. If resolution succeeds → the edit is applied and the file version increments
  4. If resolution fails → CONFLICT error with diagnostics

This is “optimistic” because the common case (no conflict) is fast—just a version number comparison. The pessimistic case (conflict) is handled gracefully with re-read suggestions.

CAS flow for multi-agent:

Agent A: OBSERVE("auth.py")                    → anchors at version 5
Agent B: OBSERVE("auth.py")                    → anchors at version 5
Agent A: PATCH(anchor="a_1", cas_version=5)    → succeeds, file now version 6
Agent B: PATCH(anchor="a_2", cas_version=5)    → CAS FAIL: version is now 6
Agent B:   ↳ re-OBSERVE, get fresh anchors at version 6
Agent B: PATCH(anchor="a_2_new", cas_version=6) → succeeds

Without CAS, Agent B’s edit would silently apply at potentially wrong positions.

8.3 File Watching

The File Manager optionally watches tracked files for external changes using OS-level file notification (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows):

  • When an external change is detected, the file version is incremented
  • All cached indices for that file are invalidated
  • Existing anchors for that file are marked stale (but not deleted—they can still be resolved)
  • If an agent tries to use a stale anchor, the resolution engine kicks in automatically

This means SCA handles the “user edits a file in their IDE between agent turns” case transparently. The agent’s anchors still resolve (unless the user deleted the target code), and the agent is warned about staleness.

8.4 Anchor Invalidation Strategy

When a file is modified, not all anchors to that file are equally invalid:

Change Type Impact
Edit within anchor’s target Contextual hash changes, but structural path still valid
Edit before anchor (in same file) Positional layer shifts, structural + contextual still valid
Edit after anchor No impact on anchor
Rename of anchor’s target Structural path breaks, but contextual hash still valid
Delete of anchor’s target All layers break—CONFLICT
File reformatting Positional shifts everywhere, but structural + normalized contextual survive

The system tracks which byte ranges were modified and uses this to provide a staleness hint on each anchor without re-resolving:

FRESH      — file version matches, anchor is known-good
LIKELY_OK  — file changed, but not in anchor's byte range
STALE      — file changed in anchor's byte range, resolution needed
INVALID    — file was deleted or renamed

This lets the model make informed decisions about which anchors to refresh (re-OBSERVE) before patching.

8.5 Multi-File Atomicity

Some operations span multiple files (rename with scope="project", or a refactoring that moves code between files). These need atomic multi-file commits:

1. Acquire write locks on all affected files (ordered by path to prevent deadlock)
2. Resolve all anchors across all files
3. If any resolution fails → release all locks, report CONFLICT
4. Apply all mutations
5. Increment version counters for all affected files
6. Store inverse operations for all mutations (as a single undo group)
7. Release all locks

The undo for a multi-file operation is also atomic—COMMIT(action="undo") reverts all files in the group.

9. Failure Modes & Recovery

9.1 Design Philosophy

SCA is designed around the principle that failures should be as useful as successes. An error response should give the model everything it needs to recover without starting over. Concretely, every error includes:

  1. What happened — a clear description of the failure
  2. Where it happened — an anchor (possibly stale) pointing to the problem area
  3. Why it happened — the resolution engine’s diagnosis
  4. What to do next — a concrete suggested recovery action

9.2 Failure Taxonomy

RESOLUTION_FAILED: Anchor cannot be resolved

{
  "error": "RESOLUTION_FAILED",
  "anchor": "a_7f3c",
  "diagnosis": "Structural path 'auth.session:SessionManager.validate_token' not found. Class SessionManager exists but has no method 'validate_token'. Nearest match: 'verify_token' (Hamming distance 2 from contextual hash).",
  "candidates": [
    {"anchor": "a_new1", "path": "auth.session:SessionManager.verify_token", "confidence": 0.85}
  ],
  "suggestion": "The method appears to have been renamed to 'verify_token'. Use anchor a_new1 instead."
}

Recovery: the model uses the suggested anchor.

CAS_CONFLICT: File version mismatch

{
  "error": "CAS_CONFLICT",
  "anchor": "a_7f3c",
  "expected_version": 5,
  "actual_version": 8,
  "diagnosis": "File auth/session.py has been modified 3 times since this anchor was created.",
  "changes_summary": "Lines 37-52 (anchor's region) were modified. The method signature changed.",
  "suggestion": "Re-OBSERVE the file or anchor to get fresh anchors."
}

Recovery: re-OBSERVE, get fresh anchors, retry.

AMBIGUOUS_RESOLUTION: Multiple candidates with similar scores

{
  "error": "AMBIGUOUS_RESOLUTION",
  "anchor": "a_7f3c",
  "candidates": [
    {"anchor": "a_new1", "path": "auth.session:SessionManager.validate_token", "confidence": 0.7},
    {"anchor": "a_new2", "path": "auth.cache:CacheManager.validate_token", "confidence": 0.65}
  ],
  "suggestion": "Multiple 'validate_token' methods found. Specify which one by using a more specific scope or one of the candidate anchors above."
}

Recovery: the model picks the right candidate based on context.

SYNTAX_ERROR: Patch would produce invalid syntax

{
  "error": "SYNTAX_ERROR",
  "anchor": "a_7f3c",
  "diagnosis": "Applying this patch would produce a syntax error at line 45: unexpected indent.",
  "preview": "... (3 lines of context around the error) ...",
  "suggestion": "Check indentation of the content parameter. The target context expects 8-space indent."
}

Recovery: the model fixes the indentation and retries. (Note: SCA’s auto-indent should prevent most of these, but the model can override auto-indent, and then this catches the mistake.)

STRUCTURAL_CONFLICT: Patch would break code structure

{
  "error": "STRUCTURAL_CONFLICT",
  "anchor": "a_7f3c",
  "diagnosis": "Replacing this method would leave a dangling decorator '@require_auth' on line 36 that is not attached to any definition.",
  "suggestion": "Include the decorator in your replacement content, or use the parent anchor a_7f3c_parent which covers the decorator + method."
}

Recovery: the model adjusts its edit scope.

9.3 Recovery Patterns

The system is designed so that common recovery follows a simple pattern:

1. Try PATCH → get error
2. Error includes a suggestion → follow it (often just using a different anchor)
3. If suggestion doesn't apply → re-OBSERVE the relevant scope → get fresh anchors → retry

The worst case is a full re-OBSERVE + re-PATCH cycle, which costs one extra round-trip. Compare this with str_replace failures, which often require the model to re-read the file, understand what went wrong, figure out the right text to match, and retry—a process that frequently takes 3–5 attempts and still fails.

9.4 Defensive Validation

PATCH optionally runs a quick syntax check (tree-sitter parse) after applying the edit. If the result has new syntax errors that weren’t present before, the edit is automatically rolled back and a SYNTAX_ERROR is returned. This prevents the accumulating-errors problem where one bad edit makes subsequent edits progressively harder.

PATCH(anchor="a_7f3c", operation="replace", content="...", validate=true)

The validate flag defaults to true for replace operations and false for insert/delete (where partial syntax errors during multi-step edits are expected).

10. Worked Examples

10.1 Bug Fix: Add Error Handling to Token Validation

Task: The validate_token method returns False for empty tokens, but it should raise InvalidTokenError.

With str_replace (current approach):

Turn 1: read_file("auth/session.py")                    # 3,000 tokens of file content
Turn 2: str_replace(
          path="auth/session.py",
          old_str="    def validate_token(self, token: str) -> bool:\n        if not token:\n            return False",
          new_str="    def validate_token(self, token: str) -> bool:\n        if not token:\n            raise InvalidTokenError('empty token')"
        )
# Risk: whitespace mismatch, stale content, ambiguous match
# Token cost of old_str: ~50 tokens (pure waste)

With SCA:

Turn 1: OBSERVE(target="auth/session.py", lens="signatures")    # 300 tokens
        → sees [a_7f3c] validate_token

Turn 2: OBSERVE(target="a_7f3c", lens="scope")                  # 200 tokens
        → sees the method body with sub-anchors:
          [a_7f3c.1] if not token: return False
          [a_7f3c.2] if self._check_expiry(token): return False

Turn 3: PATCH(anchor="a_7f3c.1", operation="replace",
              content="if not token:\n    raise InvalidTokenError('empty token')")
        → applied, returns refreshed anchor + inverse

Token savings: ~2,500 tokens saved (no full file read, no old_str reproduction).
Reliability: No whitespace matching. No ambiguity. Anchor points exactly to the if not token block.
Turns: Same number (3), but each turn is cheaper and more reliable.

10.2 Refactoring: Rename Method Across Project

Task: Rename validate_token to verify_token everywhere.

With str_replace (current approach):

Turn 1: grep for "validate_token" across project             # find all references
Turn 2-N: str_replace for each file that references it        # N sequential edits
# 6 files × 2 occurrences average = 12 str_replace calls
# Each requires exact text reproduction of the surrounding context

11.2 Detailed Comparisons

vs. Anthropic str_replace (Claude Code’s text_editor tool)

str_replace is the simplest possible approach: find exact text, replace with new text. Its strength is conceptual simplicity—there’s almost nothing to go wrong if the model reproduces the text correctly. But that conditional is the entire problem.

Anthropic’s own SWE-bench analysis shows that a significant fraction of failures come from the model’s edits not applying correctly, separate from the model’s reasoning quality. The Diff-XYZ benchmark (2025) demonstrated that search/replace format works best for large models but degrades sharply for smaller ones—precisely because smaller models are worse at exact text reproduction.

SCA eliminates this entire class of failure. The model’s reasoning about what to change is orthogonal to the mechanics of applying the change. SCA improves the mechanics without requiring better reasoning.

vs. Aider’s Search/Replace blocks

Aider has the most sophisticated fallback chain of any current tool: it tries exact match, then stripped match, then fuzzy match with various thresholds. This is an acknowledgment that exact matching is unreliable—but the solution is a cascade of heuristics, each with its own failure modes. Aider’s benchmarks show ~85-92% edit success rate depending on the model, meaning 8-15% of edits fail at the application stage.

SCA’s anchor system replaces Aider’s heuristic fallback chain with a principled three-layer resolution system where each layer has clear semantics and failure modes.

vs. SWE-agent’s edit command

SWE-agent uses a line-range-based edit command: specify start/end lines and the new content. This avoids the text-reproduction problem but introduces a different one: line numbers are the most fragile reference scheme possible. Every edit invalidates the line numbers of everything below it. SWE-agent mitigates this by limiting the model’s view window, but this constrains the model’s ability to reason about the broader codebase.

SCA’s positional layer includes line numbers but never relies on them alone. Structural paths survive edits. Contextual hashes survive reformatting.

vs. Codex CLI’s apply_patch (unified diff)

OpenAI’s approach is to have the model generate a unified diff, which is then applied. This works well when the model generates a correct diff—but unified diffs are a format designed for human review, not machine generation. Models frequently produce diffs with wrong line numbers, missing context lines, or malformed headers. The Diff-XYZ benchmark found unified diff format to be the least reliable for model generation.

vs. Morph Fast Apply

Morph’s approach is clever: the model generates “lazy edit markers” (abbreviated representations of unchanged code), and a specialized fast-apply model fills in the complete file. This outsources the exact-text-reproduction problem to a specialized model that’s good at it. The trade-off is latency (two model calls) and cost (the fast-apply model consumes tokens too).

SCA takes a different philosophical position: instead of making the model better at the current task (reproducing text), change the task so the model doesn’t have to. This is more robust because it doesn’t depend on the fast-apply model’s accuracy and doesn’t incur double latency.

11.3 What SCA Does NOT Replace

SCA is a tool interface, not an agent. It doesn’t: - Decide what edits to make (that’s the model’s job) - Plan multi-step refactorings (that’s the agent harness’s job) - Understand requirements or bugs (that’s the model’s reasoning) - Replace version control (it uses git, doesn’t replace it)

SCA replaces only the editing tool layer: the interface between “the model decided to make this change” and “the change is applied to the file.” Everything above (reasoning, planning, validation strategy) and below (filesystem, git) stays the same.

SCA parses files on demand, not upfront. The first OBSERVE of a file incurs a parse cost; subsequent operations on the same file use the cached tree (until the file changes). This means SCA scales to arbitrarily large projects—you only pay for the files you touch.

12.4 The Tool Count Trade-Off

A recent analysis (“More Agents, More Tools, Worse Results,” 2026) argues that every tool definition consumes context tokens and increases decision complexity for the model. SCA has 5 tools where str_replace has 1. Is this a problem?

The argument is nuanced: 1. Tool definitions are a one-time cost. The 5 SCA tool schemas cost ~500 tokens in the system prompt. The savings per edit cycle (~1,000+ tokens) amortize this after 1–2 edits. 2. Fewer decision points per edit. With str_replace, the model must decide what text to match (hard) and what text to write (easy). With SCA, the model decides which anchor to target (easy—it just picks from a list) and what to write (easy). The hard decision is eliminated. 3. Batch operations reduce total tool calls. A rename that takes 12 str_replace calls takes 1 SCA call. Fewer calls = fewer decisions = less context consumed by tool call/response pairs.

Net effect: SCA’s 5 tools cost ~500 tokens upfront but save thousands over a session. The trade-off is decisively positive for any task requiring more than 2 edits.

13. Limitations & Open Questions

13.1 Known Limitations

1. Tree-sitter grammar coverage gaps

While tree-sitter supports 165+ languages, grammar quality varies. Some languages have grammars that don’t handle edge cases well (complex macros in C++, template metaprogramming, advanced Haskell type-level programming). When the grammar fails, the structural layer degrades, and SCA falls back to contextual + positional (which still works, but with lower confidence).

Mitigation: The tiered support model (Section 7.1) sets expectations. For Tier 3 languages, SCA is still better than nothing (contextual hashing alone beats exact text matching), but users should expect lower reliability.

2. Anchor proliferation

A 1,000-line file might contain 200+ anchors (every function, class, method, if/for/try block, significant statement). Showing all of these to the model would consume more tokens than just showing the code. The lens system mitigates this by showing only relevant anchors at the right granularity, but the system must make smart choices about what to anchor.

Mitigation: Anchor granularity is controlled by the depth parameter in OBSERVE. Default depth of 2 means “classes and their direct methods” but not “every if-block inside every method.” The model can zoom in with scope lens when it needs finer granularity.

3. Semantic MATCH is expensive and imprecise

The semantic search mode (natural language queries resolved via embeddings) requires embedding the codebase, which is slow on first use (~30s for 100 files) and produces results that are merely “relevant,” not “correct.” The model may need to review multiple candidates.

Mitigation: Semantic mode is optional and clearly labeled as heuristic. The other three MATCH modes (text, structural, reference) are deterministic and fast. Embeddings can be cached and incrementally updated.

4. Model must learn the tool interface

SCA’s interface is more complex than str_replace. The model needs to understand lenses, anchors, operation types, and the snapshot/validate workflow. This requires either training data (fine-tuning on SCA interactions) or careful system-prompt engineering.

Mitigation: The model-facing interface is designed to be intuitive: - Anchors look like [a_7f3c] inline in code output—the model sees them in context - Tool names are verbs: OBSERVE, MATCH, PATCH, COMMIT, VALIDATE - The most common workflow (OBSERVE → PATCH) is just two calls - Error responses include literal suggested next actions

In practice, large models (Claude Opus, GPT-4-class) can use novel tool interfaces effectively with good system prompts. SCA’s interface is simpler than many real APIs the models already use successfully.

5. No type-level intelligence

SCA’s reference mode in MATCH finds textual references to symbols, not type-checked references. It can’t follow method calls through interfaces, resolve generic types, or trace data flow. This means rename operations might miss some references in highly dynamic or polymorphic code.

Mitigation: SCA is not trying to be a language server. For projects that need full type-aware refactoring, the VALIDATE tool can invoke the actual language server or type checker to catch missed references. SCA provides the 80% case (syntactic references); the type checker catches the remaining 20%.

13.2 Open Design Questions

Q1: Should anchors be persistent across sessions?

Currently, anchors are session-scoped. But for long-running tasks (multi-day refactoring, ongoing maintenance), persistent anchors could be valuable. The challenge is that persistent anchors must survive arbitrary file changes, which the resolution engine can handle in principle but which would require a persistence format and a garbage collection strategy.

Tentative answer: Not in v1. Session-scoped anchors are simpler and sufficient for current agent workflows. If needed, a COMMIT(action="export_anchors") could serialize the anchor store for later reimport.

Q2: How should SCA handle generated code?

Files generated by tools (protobuf stubs, ORM models, build artifacts) shouldn’t be edited directly. SCA could detect these (via .gitignore, header comments, or explicit configuration) and warn the model.

Tentative answer: Add a generated: true flag to OBSERVE output for detected generated files, with a warning that edits will be overwritten.

Q3: Should PATCH support declarative edits?

Instead of replace with full new content, could the model say “add parameter timeout: int = 30 to this function signature”? This would be a higher-level operation where the model specifies intent and the tool figures out the syntax.

Tentative answer: This is appealing but risky. The tool would need to understand language syntax deeply enough to generate correct code, which approaches the complexity of a language server. Better to keep PATCH as a structural-location + text-content interface and leave code generation to the model. The wrap operation is the closest SCA gets to declarative editing, and it works because {body} is a simple placeholder, not a semantic transformation.

Q4: What about non-text edits?

Some edits are better expressed structurally: “move this method from class A to class B,” “extract this block into a new function,” “inline this variable.” Should SCA support these as first-class operations?

Tentative answer: Not in v1, but the anchor system makes them possible in v2. A move operation would be: resolve source anchor, resolve destination anchor, delete at source, insert at destination, update references. This is a composition of existing PATCH operations that could be packaged as a higher-level command.

Q5: How does SCA interact with LSP (Language Server Protocol)?

Many developers have LSP running in their editor. SCA could potentially delegate reference searches and rename operations to the LSP server for higher accuracy.

Tentative answer: SCA should optionally integrate with LSP when available, falling back to its own tree-sitter-based analysis when not. The interface is the same (anchors in, anchors out); only the implementation changes.

14.4 Compatibility Strategy

SCA doesn’t require a hard cutover. It can coexist with existing tools:

  1. Shim mode: An adapter that accepts str_replace calls and translates them to OBSERVE + PATCH internally. The model keeps its existing interface; SCA handles resolution behind the scenes. This gives the staleness/CAS benefits without changing the model’s behavior.

  2. Hybrid mode: Both str_replace and SCA tools are available. The model uses str_replace for simple edits and SCA for complex ones (multi-file rename, structural exploration).

  3. Full SCA mode: Only SCA tools are available. The model uses the full lens + anchor + patch workflow. This gives maximum token savings and reliability.

The recommended rollout is: shim mode for validation → hybrid mode for comparison → full SCA mode once benchmarks confirm superiority.
