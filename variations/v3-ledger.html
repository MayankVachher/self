The core problem was a race condition between the token refresh cycle and the session validation middleware. When a user's access token expired, two things happened simultaneously: the refresh interceptor fired off a request to /auth/refresh, and the session check middleware tried to validate the now-expired token. About 15% of the time, the session check would fail before the refresh completed, killing the session entirely.


The fix is a promise-based queue. I added a RefreshQueue class in src/auth/refresh.ts that acts as a gatekeeper. When the first request detects an expired token, it acquires the lock and starts the refresh. Every subsequent request that hits the expired token during that window just awaits the same promise. Once the refresh resolves, all queued requests replay with the new token.


The session middleware now checks the queue state before validating. If a refresh is in-flight, it waits for resolution rather than immediately rejecting. This required moving session validation into an async wrapper so it can yield without blocking the request pipeline.


I also added a maxRetries config (defaulting to 2) so we don't loop forever if the refresh token itself is expired. After max retries, it clears the session cleanly and redirects to login with a reason=session_expired param so the UI can show the right message.


The migration is minimal: one new column on the sessions table (refresh_lock_id) for distributed environments where multiple server instances need to coordinate refreshes.

+     if (this.pending) return this.pending;
